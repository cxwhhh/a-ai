# A.ai Harness 改进路线图

> 编写日期：2026-10-23（北京时间）。
>
> 本文基于当前项目源码的静态阅读，记录后续设计与实施要求，不代表功能已经完成，也不是运行测试后的能力评估。本次仅新增本文档，没有修改业务代码、安装依赖、启动应用或调用模型。
>
> 文中的接口、字段和新增文件名均为设计建议。实施时先确认最新代码，再按任务逐项落地；不要将本文所有任务一次性执行。

## 1. 目标与使用方法

A.ai 的目标是：接收用户任务，自主选择工具、执行、观察结果、修正问题，并交付可检查、可修改和可下载的成果。

建设两条能力线：

| 能力线 | 目标 | 代表任务 |
|---|---|---|
| 支持更多任务种类 | 扩展执行环境、专业流程、外部工具和文件交付 | 制作 PPT、绘制图表、生成图片、整理 Excel、制作 Word/PDF、操作网页 |
| 现有任务更可靠 | 完善参数、状态、恢复、上下文、任务管理和验证 | 参数错误不误操作；失败能恢复；长任务不丢目标；交付有证据 |

建议按以下方式使用本文：

1. 先读第 2 节，确认项目现状。
2. 按第 4 节的里程碑选择一个任务，不同时铺开全部能力。
3. 为该任务选定第 5 节的验收用例，先确定“怎样算做好”。
4. 每次改动后记录实际验证结果和限制，通过验收后再勾选任务。
5. 使用第 6 节的任务模板，把范围交给 Claude 或 Codex。

任务优先级：**P0 = 实际执行和文件交付的基础；P1 = 长任务和成品质量；P2 = 扩展范围与规模。** 优先级表示风险和价值，具体实施顺序还需遵守依赖关系。

### 1.1 三个需要保持清楚的边界

- **模型**：理解任务、生成内容、决定调用什么工具。模型能力会影响最终表现。
- **Harness**：管理上下文、调用协议、执行、权限、恢复、任务状态、验证和交付。
- **能力包**：面向一种专业任务，组合 Skill、程序库、脚本、模板、渲染器与检查方法。

例如制作 PPT：模型组织内容，生成程序制作文件，harness 安排执行并记录结果，渲染与检查流程判断文件和页面是否可用。

## 2. 当前项目基础与实际缺口

### 2.1 已有基础

| 能力 | 当前实现 | 主要代码位置 |
|---|---|---|
| 模型接入 | Mock 与 OpenAI 兼容 Chat Completions 适配器 | `src/lib/llm/` |
| Agent 主循环 | 模型调用、工具执行、结果回填、步数预算 | `src/lib/agent/run.ts` |
| 工具系统 | 15 个工具；Schema、注册表、执行上下文 | `src/lib/agent/tools/` |
| 调度 | 相邻的 `parallelSafe` 工具并行，其余顺序执行 | `src/lib/agent/run.ts` |
| 运行反馈 | Python 运行与部分终端命令的验证反馈、有限自动修复 | `src/lib/agent/verify.ts` |
| 用户互动 | 提问、命令确认、运行中补充要求、停止 | `ask-user.ts`、`approvals.ts`、`notes.ts` |
| 持久化 | SQLite、多用户会话、设置、长期记忆、审计 | `src/lib/server/` |
| 执行环境 | Docker、macOS Seatbelt、本机模式 | `src/lib/server/sandbox.ts` |
| 界面 | SSE、参数草稿、过程记录、终端输出、产出预览 | `src/components/`、`src/lib/live.ts` |

### 2.2 应优先处理的具体缺口

| 缺口 | 当前行为 | 改进要求 |
|---|---|---|
| 参数未统一校验 | `execTool()` 主要做 JSON 解析，未统一按 Schema 校验 | 执行前拒绝缺字段和错误类型，明确指出参数问题 |
| 缺字段可能变成误操作 | `edit_file` 缺 `new_string` 可能按空字符串删除；`write_file` 缺内容可能写空；Python 缺代码可能执行空脚本 | 区分“字段缺失”和“明确传入合法空值”，不猜补写入参数 |
| 结果状态不统一 | 非零退出码、超时、拒绝可以正常返回；`isError` 主要在抛异常时设置 | 详情、行状态、失败统计和验证器使用一致的结果语义 |
| 调度缺少等待边界 | `ask_user` 到整批执行后才触发结束 | 执行前处理提问与其他操作混合的情况 |
| 调度缺少依赖失败处理 | 写入失败后，后续运行仍可能继续 | 依赖前项结果的操作分轮；必要时跳过并回馈模型 |
| 停止可能留下不完整协议 | assistant 的工具调用已保存，但停止后部分调用可能没有结果 | 为每个已记录调用补齐真实终态，恢复前检查协议完整性 |
| 验证依据偏弱 | 包含文件名的成功运行可能被视为验证过该文件 | 绑定准确路径、文件版本、验证调用与检查范围 |
| 完整历史持续增长 | `toModelMessages()` 发送全部消息 | 整理任务状态、保存长结果、压缩完整历史块 |
| 对话保存与运行恢复分离 | 消息持久化，但预算、验证器、事件队列等运行状态在内存 | 明确支持恢复哪些状态，不自动重放副作用操作 |
| 成品以字符串为主 | Artifact 主要为 Markdown、HTML、代码 | 增加文件型产出、预览、原文件下载与版本关联 |
| 文件 API 面向文本 | 全量读文件后再截断；Canvas 通过文本 Blob 下载 | 分离元数据、预览、完整二进制下载 |
| 脚本生成文件未统一登记 | 输出列表主要识别 `create_artifact`、`write_file` | Python/终端产出显式登记，核实文件存在 |
| 模型输入为文本结构 | `ChatMessage.content` 为字符串 | 自动检查页面截图前，需要支持图片输入和视觉模型 |
| 专业与外部能力未接入 | 尚无通用 Skills 加载器、MCP 客户端、浏览器操作系统 | 分阶段引入，先打通一项完整任务 |

以下概念不能互相替代：

- 长期记忆不等于本次任务的上下文管理。
- 消息落库不等于后台执行或中断恢复。
- 程序退出码为 0 不等于用户要求已经满足。
- 待办全部勾选不等于成果已经验证。
- 模型返回的 reasoning 不等于实际发生的操作。
- 有一个生成文件的函数，不等于已经具备预览、检查、返修与下载能力。

## 3. 目标工作流程

```text
用户目标与输入文件
    ↓
任务状态：目标、约束、计划、完成条件
    ↓
按需提供工具与专业流程
    ↓
模型提出操作 → 参数校验 → 权限检查 → 调度与执行
    ↓
结构化结果、错误、完整日志引用、文件产出
    ↓
更新任务状态 → 判断是否继续、恢复、询问或验证
    ↓
按成果类型检查，并关联到具体文件版本
    ↓
预览、下载、变更说明、验证结果和未完成项
```

这套流程可以继续沿用现有 Next.js、TypeScript、SQLite、SSE 和 `runAgent()`。优先抽取清晰的执行与状态职责，避免一次重写全部架构。

### 3.1 推荐的最小数据契约

以下是需要表达的概念，不要求一次建立全部表或照抄字段名：

| 对象 | 需要记录的内容 |
|---|---|
| 工具调用 | 调用 ID、所属运行、工具名、已校验参数、状态、开始结束时间 |
| 工具结果 | 实际结果、错误类别、退出码、摘要、完整日志引用、产出引用 |
| 任务状态 | 目标、最新约束、计划、关键发现、修改记录、剩余问题、预算 |
| 文件资产 | 文件 ID、用户与会话归属、相对路径、类型、大小、版本、来源调用 |
| 验证记录 | 被验证对象与版本、检查方法、调用 ID、结果、检查范围与限制 |
| 运行记录 | 运行 ID、会话 ID、当前阶段、等待原因、事件序号、取消与恢复状态 |

新字段首先考虑可选和兼容读取。保留旧消息的 `content`、`artifactId` 和原始执行输出；不要让新增状态导致失败日志无法展示。

## 4. 分阶段实施安排

### 总体顺序

| 里程碑 | 目标 | 依赖 | 阶段出口 |
|---|---|---|---|
| M0 | 建立基线与验收方法 | 无 | 知道当前行为、测试入口和比较条件 |
| M1 | 工具执行可靠性 | M0 | 参数、状态、等待、取消、恢复语义正确 |
| M2 | 任务状态、上下文与后台运行 | M1 | 长任务可追踪，断线与取消行为明确 |
| M3 | 文件输入与交付 | M1；长处理复用 M2 | 文件能上传、登记、预览和完整下载 |
| M4 | PPT 与确定性绘图 | M1、M3；耗时任务依赖 M2 | 两项任务能生成、检查、修改和交付 |
| M5 | 通用 Skills、MCP、AI 图片与浏览器 | 相关前置能力 | 新能力可以按需接入并保持执行边界 |
| M6 | 工程协作与持续优化 | 持续开展 | 变更可审阅，改进有评测依据 |

M2 与 M3 在共享契约稳定后可以分开推进。优先交付小规模 PPT 和图表的完整流程，不必等 M5 的所有扩展完成。

### M0：建立基线与验收方法

#### M0-01 · 确认环境与当前行为（P0）

- [ ] 确认 Node 版本满足 `package.json` 的 `>=22.13`，确认 Python、Docker 和实际沙箱模式。
- [ ] 确认当前目录的版本管理与可恢复备份方式，不假设已经存在 Git 仓库。
- [ ] 在临时数据目录和测试账号下建立样例文件，不用真实会话、密钥和用户工作区做破坏性测试。
- [ ] 运行现有 `npm run typecheck`、`npm run build`，分别记录通过、失败或受环境限制；本文未运行这些命令。
- [ ] 把 README、注释与现代码不一致之处记入待修订清单，包含 SQLite 存储、工具数量和未实际实现的适配行为。

#### M0-02 · 建立最小回归与评测入口（P0）

- [ ] 为执行器、消息协议、取消、文件交付等关键行为增加可重复测试。
- [ ] 用可控制返回值的假 provider 测试调度，不只依赖现有 Mock 固定剧本。
- [ ] 当前没有 `test` 脚本；实施时选定适合现有项目的测试入口，再写入 `package.json`，不要直接假定 `npm test` 可用。
- [ ] 建立真实模型任务集，固定输入文件、模型标识、设置、环境和预算，再比较效果。

**验收：** 同一输入可复现同一类基础行为；能区分工具实现问题、harness 问题、模型问题和环境问题。Mock 演示成功不能代替真实任务成功率。

### M1：工具执行可靠性

#### M1-01 · 执行前参数校验（P0）

**实施：** 复用工具的参数 Schema，在执行入口统一检查顶层 object、必填字段、类型、枚举和数组元素。逐步补充明确的范围约束。参数错误返回字段路径与期望，不自动猜补内容、路径或写操作参数。

**涉及：** `src/lib/agent/run.ts`、`src/lib/agent/tools/types.ts`、`src/lib/llm/types.ts`、各工具 Schema；可抽出独立校验模块。

**验收：** 缺 `edit_file.new_string` 不修改文件；明确传入 `new_string: ""` 仍允许合法删除；缺 `write_file.content` 不清空文件；缺 Python code 不启动空脚本。

#### M1-02 · 统一执行状态与错误结构（P0）

**实施：** 工具按自身语义报告结果，执行层统一记录。至少区分准备、等待确认、执行中、成功、失败、超时、拒绝、取消、跳过；结果不确定时单独标记并要求核实。错误带类别、可见说明和可选恢复建议。

**涉及：** `tools/types.ts`、`run-command.ts`、`run-python.ts`、`run.ts`、`shared.ts`、`Trace.tsx`、`OutputsCard.tsx`、`api/usage/route.ts`。

**验收：** 命令退出码 1 在详情、任务面板和统计中语义一致；失败时原输出仍能展开；搜索无匹配不一概算运行失败；拒绝和取消不计为成功，也不混同程序错误。

#### M1-03 · 等待、依赖失败与取消边界（P0）

**实施：**

- 执行前检查混合调用：`ask_user` 与其他操作同轮出现时，不提前执行那些操作，反馈模型重新组织；提问成功才进入等待。
- 需要前一步结果的操作要求分轮。关键变更失败后，后续依赖操作不能继续验证旧文件；首期可采用保守规则，无需完整依赖图。
- 每个已经记录的 assistant tool_call 都有对应 tool result，包括未执行的 cancelled/skipped。不要因停止、异常或跳过而留下悬空调用。
- 已启动的写操作在取消后可能结果不明，记录事实并先检查，不能伪造“没有执行”或直接重放。
- 控制并发上限；同一会话的并发运行需要明确限制或排队，避免消息顺序和文件相互覆盖。

**涉及：** `run.ts`、`ask-user.ts`、`approvals.ts`、`sandbox.ts`、`api/chat/route.ts`、`store.ts`、前端停止与事件处理。

**验收：** “询问是否覆盖 + 写文件”同轮时不写入；写文件失败后不运行依赖它的验证；执行前、审批中、并行部分完成和批次间停止后，再次对话均能构造合法历史。

#### M1-04 · 有界错误恢复与重复失败检测（P1）

**实施：** 记录工具名、规范化参数、错误类别和相关状态。确定性错误在没有新信息时重复出现，应提示重新读取、调整参数或换方法。临时网络错误允许有限重试；拒绝不自动重试；写入结果不明先查询。重试计入预算并记录关联调用。

**验收：** 相同失败不会一直消耗步数；修改文件后重新读、重新测试和合理的状态查询不被误拦；任何自动重试都有次数上限与取消出口。

#### M1-05 · 验证证据与完成状态（P1）

**实施：** 验证记录绑定准确路径和文件版本/内容摘要，并记录检查命令、调用 ID、结果和覆盖范围。文件再次修改后，旧检查不再代表新版本。任务收尾区分完成、部分完成、受阻、取消和未验证；待办状态只是计划，不单独作为完成证据。

**涉及：** `verify.ts`、`run.ts`、`todo.ts`、`shared.ts`、`Trace.tsx`。

**验收：** `print("a.py")` 不算运行验证 a.py；不同目录同名文件不混淆；构建通过不等于浏览器交互已验证；修复预算用尽后如实交付已有结果和剩余问题，不无限阻止结束。

### M2：任务状态、上下文与后台运行

#### M2-01 · 本次任务的工作状态（P1）

- [ ] 保存目标、用户最新约束、当前计划、关键发现、已读/已改文件、失败方法、剩余问题和产出引用。
- [ ] 每步执行后更新；用户补充要求在下一步纳入；约束变化使过时计划或验证明确失效。
- [ ] 简单问答不强制创建复杂计划；长期偏好记忆与本次工作状态分开。

**涉及：** `run.ts`、`notes.ts`、`shared.ts`、`server/db.ts`；先定义状态结构与恢复规则，再决定是否新增表。

#### M2-02 · 长输出保存与上下文压缩（P1）

- [ ] 长日志完整保存到当前用户的任务目录，模型先看到摘要、头尾及可检索引用。
- [ ] 结合估算 token 与 API usage 管理上下文预算，给下一轮工具结果和最终回答预留空间。
- [ ] 压缩保留目标、约束、路径、关键结果、计划、产出、验证与未解决问题；较早原文仍可检索。
- [ ] 按完整消息协议块处理 assistant tool_calls 和全部 tool results，不截断其中一半、不修改调用 ID、不把未完成调用藏进摘要。
- [ ] 模型需要的 reasoning 回传规则由 provider 管理，压缩不能破坏所选服务的协议要求。

**涉及：** `run.ts` 的 `toModelMessages()`、`tokens.ts`、`llm/providers/`、设置与上下文显示。

**验收：** 压缩后能继续调用工具；并行结果乱序、用户补充和取消后的历史仍合法；长日志中的关键报错能按引用取回。

#### M2-03 · 后台任务与分阶段恢复（P1）

- [ ] 引入运行 ID、任务状态、事件序号，支持查询进度、取消和重新订阅事件。
- [ ] 把浏览器断线和用户明确取消分开处理；调整当前直接使用 `req.signal` 的生命周期关系。
- [ ] 先实现单服务进程内的后台任务，再实现持久阶段状态与服务重启后的识别。
- [ ] 重启后区分可安全重做的读取、已经完成的写入、未知结果和仍在外部运行的任务；禁止盲目重放。
- [ ] 长任务分阶段设超时与资源预算，失败保留已完成文件和可用日志。

**涉及：** `api/chat/route.ts`、`run.ts`、`notes.ts`、`approvals.ts`、`sandbox.ts`、数据库与 `Workspace.tsx`。

**验收：** 刷新页面能重接同一运行而不新开重复任务；取消后确实停止；服务重启后如实显示中断状态；恢复前核实副作用。首期不承诺从任意代码位置无损继续。

### M3：文件输入、产出登记、预览与下载

#### M3-01 · 文件型产出与版本（P0）

- [ ] 保留现有字符串 Artifact，新增文件型资产的元数据和统一登记入口。
- [ ] 文件本体保存在工作区/任务目录；数据库保存归属、相对路径、类型、大小、版本、来源调用、预览和验证引用。
- [ ] 登记时实际检查文件存在、格式与访问范围，不凭模型声称或日志中的路径认定文件已生成。
- [ ] Python、终端和专业工具都能登记产出；区分可编辑源文件、预览与最终导出件。
- [ ] 修改产生明确版本关系；验证记录绑定版本；删除与清理不得误删其他任务共用资源。

**涉及：** `shared.ts`、`tools/create-artifact.ts` 或新增登记工具、`server/store.ts`、`server/db.ts`、`outputs.ts`。

#### M3-02 · 输入上传与原文件下载（P0）

- [ ] 增加文件上传入口与聊天附件引用，设定明确大小限制和文件名处理方式。
- [ ] 分离元数据查询、预览和原文件下载；下载流保留完整字节，使用正确 MIME 与下载文件名。
- [ ] 所有接口校验当前用户、文件归属和解析后的真实路径；处理软链接越界，继承现有用户隔离。
- [ ] 避免全量读大文件后才截断；不要把二进制内容当文本或把截断预览作为下载文件。

**涉及：** `api/files/route.ts` 或新增文件路由、`agent/tools/files.ts`、`ChatPane.tsx`、`Workspace.tsx`、文件资产存储。

**验收：** PPTX/XLSX/PDF/PNG 下载前后的字节哈希一致；大文件不会被 200KB 文本预览限制截断；其他用户、越界路径和越界软链接无法读取。

#### M3-03 · 预览和产出卡片（P1）

- [ ] 图片显示缩略图与大图；PDF 显示页面；PPT 使用渲染页面预览；Excel 先支持工作表数据预览。
- [ ] 预览失败不阻止原文件下载；预览不能代表已经完成质量检查。
- [ ] 产出卡展示文件类型、大小、版本、来源步骤、检查状态和下载入口。
- [ ] 操作过程展示“目的、实际对象、结果、验证”，原参数和日志按需展开。
- [ ] 参数草稿标记准备调用，真实启动后才标记执行中；摘要不能复用已经过时的 reasoning 冒充当前状态。

**涉及：** `Canvas.tsx`、`FileDrawer.tsx`、`OutputsCard.tsx`、`Trace.tsx`、`live.ts`、`Workspace.tsx`。

### M4：先打通 PPT 和确定性绘图

#### M4-01 · 专业运行环境与最小能力包（P1）

- [ ] 在执行沙箱中安装和固定所选生成、绘图、渲染程序及中文字体；只在主 Web 服务安装依赖不等于沙箱可用。
- [ ] 优先复用现有 Python 链路评估 `python-pptx`、Matplotlib；如选 JavaScript 方案，需显式为沙箱提供 Node 与对应依赖。
- [ ] 为 PPT 和图表分别准备简短操作流程、样例、模板、脚本入口和检查规则。首期可按任务明确加载，不必先完成通用插件平台。
- [ ] 增加能力探测：模型能查询哪些生成器、渲染器和服务可用；缺依赖时给出具体结果，不假报已支持。
- [ ] 验证字体缓存、临时目录、渲染器用户配置目录在只读沙箱中的可写位置，以及并发渲染是否相互干扰。

**涉及：** `Dockerfile.sandbox`、`.env.example`、必要部署配置；专业资源目录为建议新增，具体位置实施时确定。

#### M4-02 · PPT 的完整制作与返修流程（P1）

建议首期支持：封面、标题正文、双栏、图表、图片和总结等常用页面；文字及适合的原生图表可编辑。

```text
读取输入资料 → 组织页面大纲 → 选择模板与布局
→ 生成 PPTX → 检查结构 → 渲染页面
→ 检查页面 → 修正 → 登记最终版本 → 预览与下载
```

- [ ] 文件生成后重新打开检查页数、内容、图片引用和基本结构。
- [ ] 渲染出页面图片或 PDF；检查是否有字体缺失、内容越界、遮挡、图片失真等问题。
- [ ] 用户要求修改某页时，识别当前版本，修改相关内容，重新生成受影响预览与验证。
- [ ] 固定生成器适合稳定模板；允许模型在沙箱中编写代码处理特殊需求，但统一经过文件登记和验证。
- [ ] 生成、渲染与视觉检查分别记录状态。脚本执行成功不能直接标记“排版检查通过”。

**验收：** 从提供的资料制作 8～10 页 PPT，文件可打开、可编辑、可预览下载；修改第 3 页后形成明确的新版本，并能确认其他页面是否受影响。

#### M4-03 · 数据图表与流程图（P1）

- [ ] 数据绘图读取真实数据并检查字段、缺失值、单位和汇总方式；保存图表数据、绘图代码和导出文件。
- [ ] 首期支持折线、柱状、散点等常用图表，导出 PNG/SVG/PDF；检查中文字体、标签、图例、边距与尺寸。
- [ ] 无数据时明确说明需要数据或标记为示例，不编造真实结果。
- [ ] 流程/架构图保留结构化源文件，检查节点、连线和可读性，再导出图形。
- [ ] 图表可复用到 PPT，标明是可编辑原生图表还是插入的图片。

**验收：** 相同数据重复运行得到一致的计算结果；导出图片有效且标签清楚；修改数据或样式后产生新版本，PPT 不引用过时图表。

#### M4-04 · 图片输入与视觉检查（P1）

- [ ] 扩展模型消息为兼容文本与图片的结构，并为 provider 声明相应能力；保留纯文本模型可用性。
- [ ] 支持受控地把已渲染页面或参考图片交给视觉模型，关联具体页、文件版本和检查结果。
- [ ] 规则检查与视觉检查分别记录；视觉检查有修复次数和成本预算。
- [ ] 没有视觉服务或没有实际检查时，明确显示“文件结构已检查，页面视觉未检查”。

**涉及：** `llm/types.ts`、provider、设置、文件读取与预览接口、验证器和过程展示。

### M5：扩展专业能力与外部服务

#### M5-01 · 通用 Skills 与能力发现（P2）

- [ ] 维护 Skill 名称、描述、适用范围和所需依赖，任务需要时加载完整说明与资源。
- [ ] 区分“说明已加载”和“执行依赖可用”；缺少渲染器或账号时不能宣称具备完整能力。
- [ ] 工具较多时再引入目录搜索与动态加载，避免每次发送全部参数定义。
- [ ] 工具和 Skill 选择仍由应用校验权限，不能因加载流程而扩大授权。

#### M5-02 · MCP 客户端（P2）

- [ ] 先接一个明确有用的只读服务，完成连接、发现、Schema 适配、调用、错误转换和断连处理。
- [ ] 使用服务命名空间避免工具重名，记录服务来源和可用状态。
- [ ] 按用户保存认证与权限，敏感凭证不进入工具结果或模型上下文。
- [ ] 后续增加写操作时复用统一确认、日志和状态体系。
- [ ] 保持当前 provider 抽象；不能假定所有兼容 Chat Completions 的服务支持厂商专用的工具搜索字段。

#### M5-03 · AI 图片、更多文档格式与浏览器（P2）

- [ ] AI 图片接入独立生成/编辑服务，支持参考图、版本、进度、预算和文件登记；与数据图表分开处理。
- [ ] 增加 Word/PDF/Excel 能力包，每种格式都有生成、重新打开、检查、预览和原文件下载流程。
- [ ] Excel 检查区分公式写入与公式实际计算，不把旧缓存值当重算结果。
- [ ] 浏览器提供导航、读取、截图与交互，维护会话状态和实际页面证据；网页抓取不能代替交互浏览器。
- [ ] 浏览器产生外部写入前遵循用户授权，不把页面文字当作控制工具权限的指令。

### M6：工程协作、版本与持续优化

- [ ] 文件修改提供可审阅差异与版本；需要恢复时先识别用户已有改动，不能回滚掉无关工作。
- [ ] 如使用检查点，明确覆盖哪些文件和操作；外部服务写入不能当作本地文件一样直接回滚。
- [ ] 统一模型、工具、反思、摘要、视觉和图像服务的用量记录，不只统计对话主调用。
- [ ] 持续使用固定任务评测；新增工具或改提示词后，检查旧任务是否退化。
- [ ] 只有单 Agent 工作流稳定且有独立子任务时，再加入多 Agent；明确文件所有权、预算和结果合并。

## 5. 最小验收清单

以下是需要执行并保存结果的用例，不是当前已通过的测试。

| 编号 | 场景 | 预期 |
|---|---|---|
| T01 | `edit_file` 缺 `new_string` | 参数错误；文件字节不变 |
| T02 | 明确传 `new_string: ""` | 允许合法删除，并返回修改结果 |
| T03 | `write_file` 缺内容、Python 缺代码 | 不写空文件、不启动空脚本 |
| T04 | 命令退出码 1、超时、拒绝 | 状态准确，日志可读，统计一致 |
| T05 | 搜索正常完成但无匹配 | 显示无匹配，模型可调整搜索 |
| T06 | `ask_user` 与写入同轮 | 写入不执行；所有调用有配对结果 |
| T07 | 前项写入失败，后项运行该文件 | 后项跳过，不能误验证旧文件 |
| T08 | 在审批、并行工具或批次间停止 | 终态真实，继续对话无悬空工具调用 |
| T09 | 确定性错误原样反复调用 | 有限反馈并改变方法；合理重试不误拦 |
| T10 | 运行 `print("a.py")`；同名不同目录 | 不能据此认定目标脚本通过验证 |
| T11 | 文件修改后再次交付 | 旧版本检查不自动覆盖新版本 |
| T12 | 压缩包含并行工具的历史 | 协议完整，目标、约束和结果可继续使用 |
| T13 | 运行中补充新约束 | 下一步遵守，收尾说明未完成影响 |
| T14 | 浏览器断线重接与明确取消 | 不混淆；重接不创建重复运行 |
| T15 | 服务重启后恢复任务 | 识别中断与未知副作用，不盲目重放 |
| T16 | 上传并下载 PPTX/XLSX/PDF/PNG | 字节完整、文件可打开、名称类型正确 |
| T17 | 其他用户、越界路径、越界软链接 | 无法访问不属于当前用户的文件 |
| T18 | Python 生成图片/PPT | 文件实际存在，并进入输出列表 |
| T19 | 制作 8～10 页 PPT，再修改一页 | 文件可编辑、版本明确、相关预览和检查更新 |
| T20 | 中文图表与真实数据汇总 | 数值可核对、标签清楚、导出有效 |
| T21 | 未配置视觉或图像服务 | 如实报告不可用或未检查，无虚假成功 |
| T22 | MCP 断线、重复名称、无权限 | 状态明确、不串用服务或凭证 |
| T23 | 修复机会或预算耗尽 | 交付已有成果、未完成项与原因，不虚报完成 |

### 5.1 如何记录一次真实任务评测

记录：任务编号、输入文件版本、模型标识与设置、环境、工具版本、执行轨迹、结果文件、验证证据、耗时、token/服务用量和失败原因。

分别统计：任务成功率、工具参数有效率、执行失败率、重复无效调用次数、产出可用率、恢复成功率和成本。拒绝、取消、缺输入应单独分类。不要把“最终回答写了完成”作为成功标准。

先获得基线，再设改进目标；避免在没有样本时承诺达到某个产品的固定百分比。模型、输入和环境变化时，不能直接把结果归因于 harness 改动。

## 6. Claude / Codex 协作与每次任务的要求

### 6.1 拆分原则

1. 每次只完成一个有清楚验收标准的任务，例如 M1-01；共享类型与结果契约先确定。
2. 同时工作时划分文件范围；避免两个 Agent 同时修改 `run.ts`、`shared.ts`、`Workspace.tsx`。
3. 一方实现、一方复核是可选方式；也可以在契约稳定后分开实现后端与界面。
4. 合并后由明确的一方运行集成检查，不能把各自通过的局部检查当作集成通过。
5. README 与学习笔记按最终实现更新，不写入尚未完成的承诺。

### 6.2 可直接复制的实施任务模板

```text
请先读取 docs/Harness改进路线图.md，并检查最新源码。

本次只实施：[任务编号与名称]
用户目标：[具体行为]
允许修改：[文件或模块范围]
保持兼容：[旧消息/旧产出/现有模型接口等]
明确不包含：[本次之外的能力]

必须满足的验收用例：[Txx...]
请补充必要的行为测试，并运行与改动相关的检查。
现有项目检查入口为 npm run typecheck 和 npm run build；
测试脚本若未建立，需要先明确新增的测试入口，不假定 npm test 存在。

结束时给出：改了什么、验证结果、未完成事项、兼容性或迁移影响。
不要读取或输出真实 API Key，不使用真实用户数据进行破坏性测试。
不要顺带实施其他里程碑。
```
